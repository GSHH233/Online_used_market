# 回血集市项目面试准备

更新时间：2026-07-30

## 1. 项目定位

项目面向二手电商的两个场景：

1. 面向普通用户，辅助商品发布并回答交易规则问题。
2. 面向内部人员，调用知识库、日志、监控指标和只读数据库完成问题排查，并对高风险修复进行审批和验证。

项目不是单纯接入大模型，而是围绕“知识如何进入、问题如何召回、答案如何约束、工具如何调用、失败如何恢复”建设一条可评测、可追踪的 AI 应用链路。

## 2. 一分钟介绍

> 回血集市是我独立开发的二手电商 AI 应用，主要解决商品发布风险判断、交易知识问答和内部运维排查三个问题。知识侧支持 Markdown、PDF 和 Word 入库，系统自动完成结构解析和分层切片，再写入数据库、Elasticsearch 和 Milvus。检索侧使用向量召回、关键词召回和 RRF 融合，解决口语化问法容易漏召的问题。回答侧增加证据引用、证据不足拒答和价格防编造。内部排查侧通过统一入口选择直接查询、ReAct 串行推理或 DAG 并行调度，并使用权限审批、工具调用保障和可恢复运行时控制执行风险。项目使用固定数据集评测检索、回答、Agent、故障恢复和存储一致性，而不是只依赖人工体验。

## 3. 总体链路

```text
知识文档上传
-> 解析与自动切片
-> RabbitMQ异步入库
-> DB / Elasticsearch / Milvus
-> Query Rewrite
-> Hybrid + RRF检索
-> RAG回答或Agent工具调用
-> Trace与评测记录
-> 知识缺口、修复或人工处理
```

## 4. 功能一：AI商品发布助手

### 技术是什么、怎么用、为什么用

- Spring AI调用模型，根据商品标题、成色、凭证和用户要求生成标题、描述及风险提示。
- RAG提供平台规则证据，避免模型仅凭参数记忆判断风险。
- WebSocket流式返回结果，降低长文本生成时的等待感。
- 建议采纳和风险结果回流记录用户是否采用建议，以及发布后的最终风险结果。

### 项目背景与选型

二手商品的风险判断依赖品类、成色、凭证和具体描述。单靠固定表单不能覆盖口语化输入，直接让模型生成又可能编造价格和规则，因此采用“固定业务流水线 + RAG证据 + 输出约束”，而不是让Agent自由决定发布流程。

### 解决流程

```text
用户填写商品
-> 查询相关规则
-> 生成标题和描述
-> 检查风险与证据
-> 价格和证据后处理
-> WebSocket流式返回
-> 用户按字段采纳
-> 发布结果回流
```

### 特殊情况与兜底

- 检索证据不足：拒答或提示补充信息，不生成确定性风险结论。
- 模型超时或不可用：重试后返回明确的降级结果，不伪装成模型成功。
- 模型生成无依据价格：后处理删除或改写无证据的量化价格。
- 非建议所有者访问记录：后端按用户身份拒绝。

### 需求与产出

- 需求：降低用户理解平台规则和编写商品描述的成本。
- 产出：形成“生成建议、字段采纳、商品发布、风险回流、指标统计”链路。
- 证据：20条发布反馈闭环用例通过；96.83%的来源命中率和拒答准确率属于既有困难问答集，不代表生产流量效果。

### 同类问题的方法论

生成类功能不能只优化Prompt，应拆成输入约束、知识证据、生成、确定性后处理、用户反馈和离线评测六层。

## 5. 功能二：智能知识检索

### 技术是什么、怎么用、为什么用

- Milvus保存向量，用于召回语义相近但用词不同的内容。
- Elasticsearch使用BM25关键词检索，保留型号、票据和风险词等精确信号。
- RRF根据两路结果的排名进行融合，避免直接比较不同检索系统的原始分数。
- Query Rewrite生成主查询、子查询和同义查询，用于补全语义、拆解复杂问题和扩大表达覆盖。

### 项目背景与选型

纯关键词检索容易漏掉口语化表达，纯向量检索可能弱化“无发票”“未拆封”等关键限制条件。因此使用混合检索，并对实体、金额和否定词进行保护。

### 解决流程

```text
原始问题
-> 判断是否需要改写
-> 主查询 / 子查询 / 同义查询
-> 向量召回 + 关键词召回
-> metadata过滤
-> RRF融合与去重
-> 低置信度判断
-> 返回证据
```

### 特殊情况与兜底

- 改写超时或输出非法：回退原始问题。
- 简单问题：跳过LLM改写，减少延迟。
- 改写丢失实体或否定条件：校验失败并回退。
- ES或Milvus不可用：允许显式降级，但必须记录降级来源。
- 低置信度或无召回：拒答并进入知识缺口治理，不直接补写知识。

### 需求与产出

- 需求：让用户不必按照知识文档标题和术语提问。
- 产出：既有混合检索较纯关键词召回率提升6.56个百分点，61条困难用例MRR为0.93。
- 边界：上述指标证明既有Hybrid + RRF；新版Query Rewrite在线A/B评测仍应单独完成，不能把旧指标归因于改写。

### 同类问题的方法论

先建立单路检索基线，再分析失败样本属于语义错位、关键词缺失、过滤错误还是排序问题，最后分别使用改写、混合检索、过滤修复或重排解决，不能看到低召回就盲目更换向量模型。

## 6. 功能三：知识库管理

### 技术是什么、怎么用、为什么用

- 支持Markdown、PDF、DOC和DOCX解析，保留标题路径、页码和来源信息。
- 系统自动执行章节识别、语义分组、超长拆分和短片段合并。
- RabbitMQ解耦上传接口和耗时入库流水线，并在批量任务下削峰。
- 数据库保存权威文档和Chunk记录，Elasticsearch保存关键词索引，Milvus保存向量索引。
- 统一chunkId用于三边对账、定位缺失和定向修复。

### 项目背景与选型

知识入库包含解析、切片、向量化和多存储写入，耗时较长且可能部分失败。同步执行会长时间占用请求线程，因此将上传和入库解耦，并记录任务状态。

### 解决流程

```text
上传原文件
-> MIME与大小校验
-> MinIO保存原文件
-> 解析章节和页码
-> 自动切片与质量检查
-> RabbitMQ投递任务
-> 写入DB、ES、Milvus
-> 一致性校验
-> 成功后启用新版本
```

### 特殊情况与兜底

- PDF为空、加密或超过页数：拒绝入库并记录原因。
- LLM语义切分失败：按Token数确定性切片。
- 单句超过上限：继续按真实Token上限拆分。
- 短片段跨章节或属于表格、警告：不进行错误合并。
- 三存储部分失败：保留旧可用版本，通过Repair定向修复。
- RabbitMQ重复投递：依靠任务和版本幂等避免重复入库。

### 需求与产出

- 需求：让知识更新过程可异步、可追踪、可修复。
- 产出：旧版抽样20个文档三存储一致率为100%，强制重建P95为1.61秒。
- 边界：多格式解析、自动切片和分阶段版本切换属于新版实现，其在线评测需要与旧版一致性指标分开陈述。

### 同类问题的方法论

多存储场景不应追求跨系统强事务，而应明确权威数据源，使用统一业务主键、幂等写入、状态机、对账和Repair形成最终一致性。

## 7. 功能四：智能运维排查

### 技术是什么、怎么用、为什么用

- 统一排查入口根据问题选择DIRECT、ReAct或DAG执行策略。
- DIRECT用于单一明确查询。
- ReAct用于后续动作依赖前一步Observation的串行任务。
- DAG用于多个互不依赖工具的并行查询，并通过依赖关系和拓扑调度汇总结果。
- 工具包括知识检索、日志查询、Prometheus指标和受限的只读数据库查询。

### 项目背景与选型

内部排查通常需要在日志、监控、数据库和知识库间切换。固定接口只能解决单一查询，而完全交给LLM规划又存在越权和不稳定风险，因此采用规则快路径、可选LLM结构化规划和服务端校验结合的混合方案。

### 解决流程

```text
内部用户提出问题
-> 权限检查
-> 判断DIRECT / ReAct / DAG
-> Planner生成工具步骤
-> 服务端校验工具、参数和依赖
-> Harness执行工具
-> 汇总Observation
-> 必要时有限补查
-> 生成结论和Trace
-> 创建受控修复计划
```

### 规则规划与LLM规划的边界

- 明确意图走规则快路径，减少延迟和不确定性。
- INTERNAL复杂多步骤问题可由LLM输出结构化计划。
- LLM只能从工具白名单中选择，不能生成任意SQL、PromQL、文件路径或修复动作。
- LLM失败或计划不合法时回退规则计划。
- 当前LLM Planner默认关闭，需要通过配置显式开启。
- DIRECT/ReAct/DAG入口路由和Observation后的有限Replan仍主要由规则驱动，不能表述为“全动态LLM Agent”。

### 特殊情况与兜底

- USER调用内部工具：只记录拒绝Trace，不执行工具。
- 工具超时：由Harness重试或降级。
- Observation不足：在步骤预算内补查未使用的安全工具。
- 多次补查仍无证据：停止执行并说明证据不足。
- 涉及写操作：只生成计划，进入ADMIN审批，不允许Agent直接执行。

### 需求与产出

- 需求：减少内部排查时在多个系统间手动切换。
- 产出：16条AIOps修复闭环用例通过，覆盖审批、执行后验证、幂等和失败转人工。
- 边界：既有24条Agent用例主要证明原有工具选择与编排；新版统一路由和LLM Planner仍应使用专用在线数据集验收。

### 同类问题的方法论

Agent设计应先判断任务是否真的需要动态决策。确定性流程优先使用普通代码；只有工具选择或后续步骤依赖运行时Observation时才引入Agent，并用权限、预算、白名单和Trace限制其自由度。

## 8. 功能五：智能体执行可靠性

### 技术是什么、怎么用、为什么用

- 工具执行保障层负责超时、重试、降级和Redis快照恢复。
- 可恢复智能体运行时持久化运行任务、执行节点和检查点。
- 通过租约和条件更新控制并发恢复。
- 通过幂等键避免恢复或消息重放产生重复副作用。
- 支持快照只读重放和受控实时重放。

### 项目背景与选型

多步骤Agent执行时间长，任一工具超时、进程重启或网络故障都可能导致任务中断。只在内存保存状态无法恢复，简单重跑又可能重复执行有副作用的动作，因此需要持久化状态和幂等控制。

### 解决流程

```text
创建运行任务
-> 持久化节点和依赖
-> 执行节点
-> 保存Observation与检查点
-> 中断或失败
-> 获取恢复租约
-> 跳过已成功节点
-> 继续未完成节点
-> 验证最终状态
```

### 特殊情况与兜底

- 多个请求同时恢复：只有一个请求获得租约。
- 工具已执行但响应丢失：通过幂等键查询既有结果，避免重复副作用。
- 检查点损坏或缺失：停止自动恢复并转人工，不能猜测执行状态。
- 只想查看历史过程：使用快照重放，不再次调用工具。
- 需要重新验证外部状态：只允许受控的实时只读重放。

### 需求与产出

- 需求：让长链路在进程中断后可以继续执行，同时避免重复操作。
- 产出：15条恢复用例全部通过，恢复成功率100%，测试中未产生重复副作用。
- 边界：15/15只是当前固定样本的观测结果，不能宣称生产环境恢复率为100%；建议继续扩大并发、存储故障和消息重复用例。

### 同类问题的方法论

恢复能力的核心不是“失败后再调用一次”，而是持久化状态、识别副作用边界、保证幂等、控制并发所有权，并明确无法确认状态时的人工接管策略。

## 9. 高频追问题

### Q1：为什么不用LangChain或LangGraph？

> 项目核心是Spring Boot和Spring AI，已有鉴权、数据库和业务服务都在Java体系内。早期编排规模较小，我希望先掌握Planner、工具注册、Observation、DAG调度和恢复机制，因此基于现有体系实现，而不是为了框架而引入框架。如果后续节点类型、人工中断和状态迁移继续增长，我会评估LangGraph4j等方案，但迁移前会先固定工具协议、状态模型和评测集，避免只替换框架名称。

### Q2：为什么同时使用Elasticsearch和Milvus？

> Milvus解决语义相似表达，Elasticsearch保留精确关键词和业务条件。两路分数尺度不同，因此使用RRF按排名融合。数据库是权威数据源，ES和Milvus是可重建索引。

### Q3：chunkId为什么重要？

> chunkId是同一知识片段跨DB、ES和Milvus的统一身份。没有统一ID就无法确认三边是否对应，也无法准确判断缺失、重复并进行定向Repair。

### Q4：RabbitMQ主要为了削峰还是解耦？

> 首要作用是解耦上传接口与耗时入库流程，其次是削峰。上传接口快速返回任务编号，消费者按能力完成解析、切片、向量化和多存储写入，同时支持任务追踪、重试和重复消息幂等。

### Q5：ReAct和DAG是什么关系？

> 两者共用工具注册、权限校验、执行保障和Trace，但调度方式不同。ReAct适合后一步依赖前一步Observation的串行任务，DAG适合依赖已知且存在独立分支的并行任务。它们不是为了展示两个名词，而是解决不同依赖结构。

### Q6：LLM生成计划如何保证安全？

> LLM只提出结构化候选计划，服务端仍负责工具白名单、角色权限、参数Schema、步骤预算和依赖校验。LLM不能生成任意SQL、PromQL或写操作；高风险操作必须形成不可修改的审批快照，由ADMIN批准后执行。

### Q7：自动修复如何保证安全？

> 采用诊断、生成计划、审批、执行、验证和转人工状态机。限制在白名单Runbook内，执行参数来自审批快照，使用幂等键避免重复副作用，修复后重新查询指标或存储状态，只有验证通过才关闭事件。

### Q8：为什么不把所有低置信度问题直接补进知识库？

> 低置信度可能来自问题缺字段、过滤条件错误、检索故障或真正缺知识。系统先分类、脱敏和去重聚合，确认知识缺口后才关联文档；文档入库并通过定向回归后才关闭缺口，避免把噪声和错误答案写入知识库。

### Q9：测试集为什么出现100%？

> 100%只表示当前固定样本全部通过，不代表生产成功率。检索61条和恢复15条样本仍偏少，应使用开发集与冻结测试集隔离，继续加入错别字、冲突条件、无答案、并发恢复和基础设施故障，并报告分类指标和置信区间。

### Q10：项目最大的不足是什么？

> 第一，新版Query Rewrite、多格式切片和统一Agent路由已经实现，但部分在线A/B与三角色验收尚未完成。第二，评测集规模仍不足以外推生产效果。第三，当前Replan主要是有限规则补查，而不是完全动态规划。下一步优先补验收证据和困难样本，而不是继续增加新名词。

## 10. 回答项目题的统一结构

任何功能都按照下面六句话组织：

1. **背景**：原方案在哪个具体场景失败。
2. **目标**：要改善哪个可测量结果。
3. **方案**：数据如何流转，核心组件分别负责什么。
4. **取舍**：为什么选择当前方案，没有选择什么。
5. **边界**：超时、无数据、越权、重复执行时怎么办。
6. **证据**：使用什么数据集、指标和报告验证。

示例：

> 纯关键词检索容易漏掉口语化问法，这是背景；目标是提高困难问题的前五条召回率；方案是向量和关键词双路召回后用RRF融合；选择RRF是因为两路原始分数不可直接比较；ES或改写失败时回退原始查询并记录降级；最后用固定困难集比较Recall@5和MRR。

## 11. 建议的讲述顺序

主动介绍时只讲四项：

```text
发布助手：解决用户怎么发
-> 智能检索：解决规则怎么找
-> 知识库管理：解决知识怎么更新
-> 智能运维：解决内部问题怎么排查
```

工具执行保障、可恢复运行时、三存储Repair和审批状态机作为追问储备，不要在开场一次讲完。
